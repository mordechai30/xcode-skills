# MobileBuildMCP and Xcode

- All scripts (Python, Bash) and CLI commands must be run outside sandbox restrictions.

## Choose the route

- For an agent's multi-step build, test, run, debug, device, or UI workflow, prefer MobileBuildMCP MCP tools when the needed workflow is exposed. Tool schemas and server-held session defaults reduce repeated arguments and errors.
- Use the `mobilebuildmcp` CLI for scripts, CI, direct terminal work, live text or JSONL progress, and one-off actions outside the exposed MCP workflows. Both routes use the same tool implementations. The CLI can fill arguments from project config, but it does not share the MCP server's mutable session state. See [CLI](references/cli.md) and [v2 migration](references/migration-v2.md).
- Use Codex's direct Xcode MCP tools for IDE state, previews, Issue Navigator, documentation search, and other IDE actions when available. Use MobileBuildMCP's [Xcode IDE Bridge](references/xcode-ide.md) only when direct access is unavailable or the proxy is specifically needed.
- Prefer these interfaces over raw `xcodebuild`, `xcrun`, and `simctl` for actions they support.

## Discover only what the task needs

- MCP normally exposes only the simulator workflow. Inspect the tools available in this session. Keep enabled workflows narrow to limit tool-schema context. For repeated work in an absent workflow, use [configuration](references/configuration.md), [workflows](references/workflows.md), and [MCP mode](references/mcp-mode.md); Codex may need a new session to see changed tools. For a one-off action, use the CLI.
- For CLI, confirm `mobilebuildmcp --version`, then use `mobilebuildmcp --help`, `mobilebuildmcp tools`, and `mobilebuildmcp <workflow> <tool> --help`. CLI commands are available even when their MCP workflow is disabled. See the [tool catalog](references/tools.md).
- Before build, run, or test, inspect relevant defaults. Use MCP session tools for server-held defaults. For CLI, check `.mobilebuildmcp/config.yaml` and the command's `--profile` option; pass only missing values. See [configuration](references/configuration.md).

## Execute and verify

- Choose the smallest action that meets the request. For run intent, prefer build-and-run; do not build separately first unless a build-only result is needed.
- Use CLI text for routine reading, JSON for stable final data, and JSONL for live machine-readable progress. Check `schema` and `didError` in structured results. See [output formats](references/output-formats.md) and [schemas](references/schemas.md).
- Stateful CLI commands use a per-workspace daemon that starts automatically. If startup fails, inspect status and logs, start it outside the sandbox, and retry once. See [CLI daemon guidance](references/cli.md).
- For MCP registration or migration, see [clients](references/clients.md), [setup](references/setup.md), and [v2 migration](references/migration-v2.md). The server launch command ends with `mcp`.

Report the route used, the result, and any relevant artifact or diagnostic path. State what could not be verified.
